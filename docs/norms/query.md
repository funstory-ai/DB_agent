# 大类：`query` — 查询类

## 判定

要**查数并给出答案或交付明细/汇总**：人数、次数、转化、字段核对、完备性占比、Excel 一人一行等。

**本类不做**：建中间表、CREATE TASK、挂 Superset 看板（那些属 `dashboard`）；原表 vs 新表加工审核属 `audit`。查数过程中撞上脏数据审查 → 可叠读 `anomaly`，但仍以 query 为主流程。

## 开查

1. 读本文件 + 相关 pitfalls + 目标表文档
2. **占需求编号**：`docs/tasks/README.md` 取下一 `T###`，建档并列入「进行中」（命名见该 README）
3. **交付形态未说明先问**：汇总数字 vs Excel 一人一行（非正式口头结论除外）
4. **细节易分歧先问（P025）**：时间窗对齐、事件范围、是否活跃、去重主体。兑换码算付费、试用另计，已由 P013 拍板，不必再问。禁止擅自加口径再当正式结论
5. **对照需求做潜在口径审查（P032，强制）**：处理变量会不会改写分母/分子？本题要完整漏斗还是条件转化？已知表约束（如 deviceinfo 仅注册）乘上本题会不会选错 join？说不清先问，禁止「表会用就开写」
6. 涉及主要翻译功能事件 → 先读 [`translate_biz.md`](translate_biz.md)
7. 映证 `docs/tasks/` 是否有相近口径

## 类内共通流程

```
需求 → 潜在口径审查(P032) → 定主体与时间窗 → 选表 → 写只读 SQL
  → 小范围核对 →（正式交付）按任务抽样复核 P019
  → 留档 tasks/reports → 清零试错
```

### 正式交付（Excel / 汇总报表）

- **正式交付**：口径写进任务文档；SQL 进 `sql/reports/`；任务文档含**需求覆盖对照**（条目→落点→✅/不做）
- **抽样**：验本任务关键断言（P019），且须对汇总数字做**合理性判断**（假零/串组/量级；见 `docs/sample_validation.md`）
- **交付验收**：对照初始需求逐项打勾后再称完成（见 `docs/norms/README.md`）

### 非正式小问（对话占比/完备性等）

- 默认抽样或 **1～7 天**短窗；标明是否抽样（P021）
- 一条 SQL 出结论；禁止半小时起步式 behaviour 串行大扫
- 禁止为小问题重跑 cohort 全量

## 查数红线（补充）

- **先问（P025）**：细节易分歧先问用户；禁止擅自加「活跃」或缩短匹配窗后，把低匹配甩给原表。
- **潜在口径（P032）**：写 SQL 前对照需求推演分母/分子/观察窗偏倚；表文档有事实 ≠ 本题口径已正确。
- **时间窗与需求对齐**：需求近 N 天，订单与行为匹配窗同对齐，除非用户另定。
- **效率（P026）**：behaviour 匹配用一次半连接；禁止默认串行大 `IN`。
- **设备级「新装 / 激活」（默认，P034）**：
  - **新装**：`event_name='init_page_daily' AND is_new_user_today='1'` → `COUNT(DISTINCT device_id)`
  - **激活**：`event_name='translate_page' AND is_new_user_today='1'`（同日激活率场景）
  - **禁止**默认用「首条 `translate_page` + `install_day`」冒充新装分母（那是激活/翻译进组，会随晚到首译膨胀已闭合安装周）
  - 看板摘要见 [`dashboard.md`](dashboard.md) §3.1；实验/漏斗分母未另说明时按本条
- **转化主体（P018-D，强制）**：转化 / 漏斗 / 转化率先归到「人」。有账号用 **userid**（同一账号多设备只算 1 人）；没有账号用 **device_id**。禁止按设备把已登录用户拆开，也禁止把无账号设备滤掉。付费分子仍是订单 userid。
- **同一设备多行账号（P018-E）**：`row_number` 必须有唯一决胜键。同一 `deviceid`、同一 `installtime`、多个 userid 时，不能随机留一行。设备粒度「付过费」= 任一关联账号有付费单。
- **已交付的格子（P044）**：解释某个已交付数字，必须用同一次查询、同一粒度、同一时间锚点。重跑变了先对差异，再决定是否替换。禁止用另一次跑的子集去减旧总数，禁止用倒推锚点的另一批人顶替这一格。
- **移动端设备表缺口（P037，强制提醒）**：`os_name` 为 android/ios/ipados（及 App UA）时，埋点 `device_id` 大部分不在 `imt_deviceinfo`。涉及移动端的结论必须写明这一点和原因，禁止只用设备表 INNER JOIN 当移动端全集。
- **注册墙类实案（P031）**：分母用**设备级埋点新装**（默认同 P034）；`deviceinfo` 只 LEFT JOIN；禁止 INNER JOIN 把未注册踢出后再比转化。
- **账号级新装转化（P033）**：勿裸用 `min(installtime)`；须按三过滤剔老号（安装前现金 / 现金早于账号 / 账龄≥30 天）；禁止用 `iospay_renew` 当老客过滤；复用 `sql/reports/query_new_install_user_filter_20260831.sql`。
- **设备级「真新账号 / 剔重装」（P039）**：
  - P034 的 `is_new_user_today` **≠** 新账号；重装老号约占激活 6%
  - **新付费墙 / 登录赠送 / 改版付费「对新用户」**：**只出剔老号一版**（`createtime < 激活−1天`），**开查不必再问**；**不要**再单独出含老号的全量对照（口径 A）
  - 刀法：userid←deviceinfo∪激活行∪本题 claim；**禁止**用 deviceinfo 时间判老号
  - 与 P033（账号级）勿混用；一般长期 AB 仅对齐历史 P034 时可不剔
- **AB / 实验须限版本（P040，默认强制）**：
  - 老客户端也可带 `ab_tag`，不等于当期实验流量；**污染不只 Rule A**
  - 开查须定 **实验起始版本**（优先）或 **近 N 版白名单**；用 semver 数值比较，❌ 禁止 `version >= '1.32.6'` 字符串比较（会漏 `1.32.10`）
  - 新用户向实验与 **P039** 叠用
- **点击→订单漏斗时差（P042，默认）**：
  - 埋点 CTA（如耗尽「去付费」）归因成单时，订单 `createtime` 相对点击**默认前放宽 1 天**（`>= 点击−1天`），上界仍受 asof 约束
  - 消化行为/订单落库时差；任务注明即可，不必再问「要不要放宽」
  - **不**改无点击锚点的累计付费；严格因果窗须另注明
- 发现低匹配：先查自身 SQL，再怀疑原表。
- **月报正文格式（强制，P041）**：见下节；禁止改成 Markdown 标题混排或把段落粘成一段。

## 刷新类分析（canonical 脚本约定）

同一分析会**定期刷新**（周漏斗、月报、促销清单等）：每刷新一次就复制一份 dated 脚本/SQL（`export_t077`→`t084`→`t085`…）是主要冗余来源，会让仓越堆越胖、且旧 dated 副本与历史数字纠缠、易误用。

**约定**：
- 这类分析只保留**一份 canonical 脚本**，把可变项（主要是 `asof` 数据日）做成**命令行参数**；刷新时只改参数、**覆盖输出**，不新增 dated 文件。
- 周切片、留存回访周等"随 asof 推进"的量**由数据推导自动收口**（P045），禁止写死。
- 落地 canonical 后，历史 dated 副本（如 `export_t085_*`）**退役**：任务文档「定稿脚本」改指向 canonical；旧 dated 脚本可删，但保留其任务文档作溯源。
- **示范**：`scripts/export_gift_weekly_funnel.py`（赠送周漏斗；`--asof` 默认 2026-10-28 复现 T090；OBS_END / 周切片 / SQL 边界全部从 asof 推导，不写死）。

## 月报正文格式（强制，P041）

核心月报（T031 / T058…）**交付正文**样板：桌面 `沉浸式翻译2026年08月核心数据.md`（纯正文，不含任务核对表）。

### 核心原则（对齐上月截图样板）

样板：飞书/文档里的「沉浸式翻译2026年08月核心数据」（只粗标题与 `1、`/`2、`/`3、`；正文数字不粗；段内连续换行）。

1. **只加粗 4 处**：大标题 + `1、` / `2、` / `3、` 小标题；**正文数字不加粗**
2. **一个指标一行**：月活 / 日活均值 / 日活峰值 / 总事件 / 网页 / 视频 / 人均 各占一行；段内**不空行**
3. **段与段之间空一行**（1/2/3 之间）
4. 「整体来看…」「注：…」各保持**一整段**（不要拆成多行）
5. 主交付 `.docx`（真实加粗）；禁止 `##`/`###`、禁止代码块包正文
6. **段末汇总必须按当月重写（强制）**：禁止把上月「整体来看 / 收入叙事 / 注」换数字照抄

### 段末分析（强制，勿套模板）

数字行可以沿用结构；**小标题 + 第 2 段「整体来看」+ 第 3 段环比叙事与「注」末句**须根据**本月相对上月/同比/季节**重新判断：

| 要写清 | 示例维度（按月选用，不必全写） |
|--------|--------------------------------|
| 趋势定性 | 止跌 / 回升 / 横盘 / 继续下滑；与上月叙事是否翻转 |
| 结构矛盾 | 如日活升但用量不动、收入跳升但 MRR 仅微增 |
| 季节/日历 | 寒暑假、开学季、春节错位、大促（618/双11）高低基数 |
| 业务解读 | 网页 vs 视频谁拖累；订阅存量 vs 当月净收入弹性 |

反例：每月都写「网页继续明显下降，仍是总用量下滑的主要来源；视频需求相对稳定」——若本月网页已近乎持平或视频转负，必须改写。

### 版式细则

1. 桌面只交纯正文，不夹任务核对表
2. **第 1 段**：小标题（当月定性）→ 月活一行 → 日活均值（末`；`）→ 日活峰值（末`。`）
3. **第 2 段**：小标题 → 总事件 → 网页 → 视频 → 人均 → 「整体来看…」一整段（**当月分析**）
4. **第 3 段**：小标题 → 环比叙事（**当月分析**）→ 同比 → 「注：…」一整段（MRR 数字可固定句式，**读法须当月重写**）
5. 数字：万 1 位小数；事件「万个」整数；比率 1 位小数；订阅整数

### 开查核对

相对上月正文结构逐项对 Excel；表内无日活均值/峰值时用业务侧给定值；周活 / PDF / EPUB 上月未写则本月亦不展开。写段末前先列「本月 vs 上月：翻转点 / 季节因素」再落笔。
