## 1. 现象（用户上报 + 本次重算）

`query_translate_page_monthly_retention_ruleA.sql` 的 2026-09 行 `new_user_count`，**三次不同日期拉取给出三个不同、且非单调的值**：

| 拉取时间 | 2026-09 new_user_count | 备注 |
|---|---|---|
| 2026-10 初 | 1,010,718 | 用户上报 |
| 2026-11 初 | 931,096 | 用户上报，Δ=−79,622（−7.9%） |
| **2026-11-03 本次重算（当前快照）** | **1,026,638** | 精确值，见 §3 Q9；稳健性窗口校验 1,029,662 / 1,026,643 |

**关键**：数字在**振荡**（↓ 再 ↑），不是单调漂移。这直接证伪"纯追加/只增不删"假设，也证伪"迟到历史持续把 min 前拉"和"install_day 只会被改早"两种早期猜测。

## 2. 已证伪的说法（必须收回）

用户指出「每分钟落表、不可能迟到一个月」并要求"猜测要有明确证据"。据此核查后，以下说法**证据不足、予以收回**：

- ❌ 旧说"install_day 被 ETL 持续向前改写"：仓库内**没有任何**写/改 `user_behaviour` 的 SQL（grep 仅见读取）；改写只发生在派生表 `imm_device_native_language`，不碰本表。
- ❌ 旧说"9 月之前的历史事件在两次拉取之间迟到进入、把 min 前拉"：**这是把『表里存在 7/8 月数据』错误等价于『这些数据是 10→11 月之间才进表的』**。表里存在历史数据 ≠ 历史数据是晚到的；在"每分钟落表、无迟到"管线下该机制不成立。
- ❌ 旧说"单调只减"：三拉取非单调（1,010,718 → 931,096 → 1,026,638），排除任何"只朝一个方向变化"的机制（迟到历史 / 只改早 / 只追加）。

## 3. 已用数据证实的事实（Q1–Q10，只读、有界）

`install_day` 是 `varchar`，原 SQL 队列月 = `to_start_of_month(min(install_day))`。逐项验证：

- **Q1（9月活动分区, 1%抽样）**：`install_day` 取值**只有** `ISO YYYY-MM-DD`（1,376,144 条）与 `1970-01-01` 占位（16,063 条）。**无** epoch 数字 / slash / 带时分秒等混合格式。
- **Q2（9月活动分区, 44,824 台）**：单台设备在**同一活动月内**多个不同 `install_day` = **0**。
- **Q6（跨 8/9/10 月活动分区, 80,713 台）**：单台设备**全局**多个不同 `install_day` = **0** → **`install_day` 是单台设备全局恒定的常量**。
- **Q3 / Q4**：字符串 `min` 与日期 `min` 的队列月**差异行数 = 0** → 纯 ISO 下字典序 min ≡ 日期 min，格式 bug 不存在。
- **Q8（9月活跃设备 install_month 分布, 1%抽样）**：9,890 台 install_month=2026-09；另有 326 台为 `1970-01-01` 占位（P003，稳定存在、非漂移源）。

> **由 Q2/Q6 推出的逻辑铁律**：同一台设备所有事件的 `install_day` 是同一个常量 ⇒ **对该设备增删事件无法改变它的队列月**（min 永远等于那个常量）。因此"某设备队列月在两拉取间变化"只有两条数据侧路径：
> - **(A)** 该设备的 `install_day` 字段值本身被改写（更早或更晚）；
> - **(B)** 该设备的事件被整批删除、或版本被改成全部 `1.11.4` → 设备在 inner 查询中整体消失（失去"≥1 条通过事件"）。
> 单纯"新增/删除部分事件"不可能移动队列月，只能让设备出现/消失。

**当前快照重算（2026-11-03，精确值，分区裁剪 `created_ts >= '2026-09-01'`，见 §9 裁剪正确性）**：

- **Q9**：当前 9 月 `new_user_count` = **1,026,638**（缓冲窗口 0825=1,029,662、严格窗口 0901=1,026,643，差 ~3k 为 UTC 边界误差，结论稳健）。
- **Q2'（当前快照 Sept-install 设备基数，含被版本/RuleA 排除者）** = **1,053,539**。
- **Q1' = 1,026,638** ⇒ 被 `version != '1.11.4'` / Rule A 过滤掉的设备仅 **26,901（2.5%）**。
- **Q3'（当前快照窗口内被版本/RuleA 完全排除的设备，跨所有队列）** = **68,868**。

**结论（确定，非猜测）**：在当前快照下，原 SQL 的队列数学**正确且确定**（`install_day` 干净、单格式、单设备常量）；9 月桶 = "install_day 月=9 月 且 ≥1 条通过过滤事件"的去重设备数。

## 4. 三拉取非单调 → 表在两次间被重写（核心结论）

9 月桶变了（−79,622 再 +95,542），而 SQL 数学确定（§3），故**底层数据在两次拉取间必然不同**。但三次值**非单调**，因此排除一切"朝单方向变化"的解释（迟到历史、只改早、只追加）。唯一与"非单调、且波动达 ~80–95k"相符的是：**`user_behaviour` 在两次拉取之间被重写 / 重建**（事件集或字段值发生变化），而非纯追加日志。

**主因收敛到 `install_day`（队列归属），不是版本过滤**：
- 当前快照里，版本/RuleA 过滤只剔除 Sept-install 设备的 **2.5%（26,901 台）**；
- 而三拉取的摆动高达 **~80–95k**，远大于 27k；
- ⇒ 摆动的主因是**队列归属（install_day）在两拉取间变动**，即机制 (A) `install_day` 字段值被改写（或等价地，设备整批被重建导致同一 device_id 的 install_day 在两次拉取间取值不同）。机制 (B)（事件整批删除 / 版本全改 1.11.4）只能解释 ≤27k 量级，非主因。

> 注意：(A) 与"设备被整批重建、重建后同一 device_id 的 install_day 取值不同"在效果上等价——都表现为"同一 device_id 的队列月在两快照间变了"。本仓只读、看不到上游重算作业，无法区分这两种实现；统称"install_day 在两拉取间被改写/重建"。

## 7. 影响与建议

- **立即（止血）**：别把它当实时数反复重拉。要唯一真值就**冻结一个 asof 快照**不再现场重算（与 P044 同源对齐）。当前 1,026,638 不等于"真值"，只是"此刻快照值"；它会再变。
- **可复现修复（见定稿 SQL）**：把每台设备的队列月**快照**到稳定表（`immdata.dim_device_install_cohort(device_id, cohort_month)`），月留存 JOIN 该表而非现场无界 `min(install_day)`。这能消除"现场重算不可复现"，**但若 install_day 本身被上游重写，则快照只反映快照时刻值**——真治本需上游确认 install_day 口径与重算任务。
- **数据质量（顺带）**：`1970-01-01` 占位仍能通过 `TRY_CAST(...) IS NOT NULL`（合法日期），会进入 1970 队列桶；若不想计入新装应显式 `install_day > '1970-01-01'`。不影响本次漂移，但属独立小坑。

## 9. 本次重算方法（裁剪正确性说明）

因 `install_day` 为单设备常量（Q2/Q6），**一台 9 月安装设备的所有事件 `created_ts` 必 ≥ 2026-09-01**（事件不可能早于安装日）。故仅扫 `created_ts >= '2026-09-01'` 即可 100% 覆盖所有 9 月队列设备，扫描量从全历史降到约 2 个月，得到**精确** 9 月桶（非抽样），约 6–9 分钟完成。

- 稳健性：窗口分别取 `2026-08-25`（缓冲，兜 UTC 8/31 边界）与 `2026-09-01`（严格），结果 1,029,662 / 1,026,643，差 ~3k，结论稳健。
- `created_ts` 仅用于**限定扫描范围**，不参与队列计算（队列仍由 `min(install_day)` 决定），故与原 SQL 语义一致。
