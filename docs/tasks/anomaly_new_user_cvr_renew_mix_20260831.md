# 异常复核：新用户「N 日首单付费」是否被老客二次付费抬高

- **需求编号**: T022
- **规范大类**: `anomaly`
- **状态**: ✅ 已完成（已纠偏）
- **日期**: 2026-08-31
- **定稿 SQL**: `sql/reports/anomaly_new_user_cvr_renew_mix_20260831.sql`
- **背景**: 要的是**新用户 N 日内首单付费转化**。曾误把 `iospay_renew` 当「老客续费」主因；业务指出 **iOS 付费单一律叫 renew**，且转化=首单付费——已验证并改口径。

## 需求覆盖对照

| 需求项 | 状态 |
|--------|------|
| 验证 iOS 付费是否都叫 renew | ✅ |
| N 日转化 = 首单付费（非「窗内任意付费」叙事） | ✅ |
| 老客二次付费是否抬高、占比 | ✅ |
| 是否「问题都由 iOS 引起」 | ✅ 否 |

## 观察口径

- 分母：`userid` 级 `min(installtime)` ∈ 2026-08
- **首单付费转化**：该 userid **lifetime 第一笔** `finished` 且 `amountpaid>0` 落在 `[install, install+N)`
- 对照「虚高」：安装后 N 日内有现金，但 lifetime 首单 **早于** install（老客又付）

## 【异常审查】

### A. iOS 付费命名（验证业务说法）

- 2026-08 全部 `iospay%` 且 `amountpaid>0`：**2880/2880 = `iospay_renew`**
- 2025-01 起有过 iospay 现金的 userid：其**第一笔** iospay 现金也是 `iospay_renew`：**9311/9311 = 100%**
- **结论**：iOS 付钱订单（含首单）在库里都叫 renew；**不能**用 `ordertype=iospay_renew` 识别老客续费，更不能当转化虚高主因。

### B. 首单付费 vs 窗内任意付费（3 日）

| 口径 | 人数 | CVR | 说明 |
|------|-----:|-----:|------|
| 安装后 3 日内有任意现金 | 634 | 0.463% | 朴素窗内付费 |
| **lifetime 首单落在安装后 3 日** | **633** | **0.462%** | 本题目标口径 |
| 虚高：窗内有付、但首单早于安装 | **1** | 占朴素分子 **0.2%** | 几乎可忽略 |

- day0（24h）：朴素 437 = 真首单 437，虚高 **0**
- 真首单渠道（3 日，多通道，非「全是 iOS」）：`normal` 279、`iospay_*` 231、`subscription` 103、`googleplay` 20
- 唯一虚高例：userid=`6982564`，同日先 `subscription` 再 `upgrade`（首单略早于 `installtime`），与「老客续费大面积混入」无关

### C. 纠偏说明

- 前一版把 renew 占分子 ~37% 讲成「续费抬高」→ **跑偏**（那是 iOS 首单的命名）
- **按首单付费**：老客二次付费几乎不进分子；当前 cohort 下**看不出转化被老客续费明显抬高**
- 若业务仍觉得 CVR「偏高」，应查：**分母是否过窄**、是否混入试用、观察窗/对比基准，而不是剔 `iospay_renew`

- **建议动作**：新用户现金转化分子用 **lifetime 首笔 `amountpaid>0`**；忽略「是否 renew」标签。iOS 与非 iOS 一视同仁。
- **是否写入 pitfalls**：待确认（建议：iOS 付费均 `iospay_renew`，勿当续费过滤条件）

## 一句话结论

**iOS 付费单确实证实全是 `iospay_renew`（含首单）。按「N 日首单付费」，8 月新装 cohort 几乎没有老客二次付费虚高（3 日仅 1 人，0.2%）；问题不是「iOS 续费把转化抬高」。**
