- **规范大类**: `anomaly`

  对象收窄为：安装前现金 gap **≥30 天** 的 29 人（短间隔落库另说）。

| 根因 | 人数 | 占比 | 是否你问的三类 |

| **F 老账号，设备行很晚才进表** | **16** | **55%** | **都不是**：不是碰撞、不是 install 刷新、不是挂账 bug。是 **用 min(installtime) 当「新用户」的口径问题**——账号/付费很早，但活设备行 createtime 全在 2026-08 且贴近 install |

### 排除项（直接回答）

1. **新装日期刷新？→ 否（0/29）**  
   活设备行上 `installtime - createtime ≥ 30 天` 为 0；行 createtime 与 install 同日或 install 略早于行（同步滞后），**不是**「旧行把 install 改到 8 月」。
2. **软删藏了旧安装？→ 否（0/29）**  
   无更早软删设备 install。
3. **大规模 id 碰撞导致？→ 不是主因**  
   互斥后仅 3 人主键落在共设备；共设备对方多无对应历史付费。

### 主因说明

**F（16 人）例：`283148`**  
- 账号 2024-03，2024 起多笔月付；`min(install)` 与唯一活设备行均在 **2026-08-14**（与 `createtime` 差约 1 分钟）  
- 结论：更符合 **迟补上报**：`installtime`≈入库/上报时刻，不是真安装日；被 `min(installtime)` 误标成 8 月新装。

**A（10 人）例：`6915779`**  
- `userinfo.createtime` = 2026-08-05，邮箱像系统生成 `…@immersivetranslate.com`  
- 同 userid 订单现金却在 **2024-12**  
- 结论：**订单 userid 与当前账号时间线矛盾**（复用 id / 错挂），属数据异常，不是「真新用户提前付费」。

### 补充（业务反馈，已用数据核对）

设备表曾有上报缺口，修复后约需等用户缓存到期（约半年）再登录才会补行。  
**`installtime` 很可能接近「终于上报/入库」的时间，而非真实首次安装。**

证据：
- 8 月 `installtime` 行中，**81%** 与行 `createtime` 相差 ≤1 小时；**87%** 同日
- F 类例：`283148` 2024-03 起付费，但 `installtime`/`createtime`/`lastlogintime` 均挤在 2026-08-14 前后几分钟
- 例 `551923`：`lastlogintime` 已有 2026-06-19，而 `installtime`/`createtime` 在 2026-08-01 → 更像补报入库，不是真·首次安装日
- 插件侧 `installedAt` 存在 sync/local；若缓存清空会重新写成 **now**（`utils/fake_user.ts`）；上报字段来自该值

因此：先前「不是 install 字段被改写」仍成立；更准确说是 **迟到的首次入库把上报时刻写成了 installtime**，导致老客被标成新装。


- **是否写入 pitfalls**：待确认（建议：禁止仅用 userid min(installtime) 定义新用户；现金早于 userinfo.createtime 标质量问题）

## 一句话结论

**≥30 天这 29 人：不是「旧行改 install」式刷新；约一半是设备迟补上报导致 `installtime`≈上报/入库时间（老客扮新装），约三分之一是现金早于账号，碰撞很少。**
