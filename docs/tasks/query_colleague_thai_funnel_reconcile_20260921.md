## 问题

同事用 Codex 跑的泰语漏斗（网页/移动端使用主体都是 5,252，现金支付 10+1）和本仓 T035/T036 对不上，SQL 还跑了约 5 小时。要先判断是不是库内数据异常。

## 结论

**不是库内数据异常。** 是漏斗 SQL 的分母和过滤，和已验收口径不是同一题。

| 对照 | 本仓已验收 | 同事这次 | 说明 |
|------|------------|----------|------|
| 近 30 日泰语使用 | T035：设备 5,507（窗 8/11–9/11，设备） | 人 5,252（窗 8/22–9/21，有账号归 userid） | 同量级。窗口和主体都不同，不应相等 |
| 端 | T035：桌面 4,447 / 移动 908 | 两行使用人数都印成 5,252 | SQL `CROSS JOIN` 把**全体**使用人数贴到网页、移动端两行 |
| 历史现金付费 | T036：152（9/10） | — | 今天重算 **156**，只是后来新付的，订单没丢 |
| 窗内现金付费 | — | 漏斗 10+1=11 | 同一窗、泰语账号、不看漏斗：**27 人**。11 是「先使用再进指定定价事件再付款」的子集 |

## 为什么会这样

1. 使用人数只算了一次 `first_use`，再 `CROSS JOIN` 到 `web` / `mobile`。两行 5,252 是同一个数，不能当成两个端的用户，也不能相加。
2. 渠道不是按 `platform_type` / `os_name` 拆的。网页 = 事件 `go_pricing_page`，移动端 = 事件 `billing_show`。使用分母没有按端拆开。
3. 支付还要求付款时间不早于该端第一次定价事件。订单表里这 30 天有 27 个泰语现金付费账号，进不了这条链的不会出现，所以不是 27，更不是 T036 的历史 156。
4. 跑 5 小时：先扫全站 30 天 `user_behaviour`（十几种翻译事件 + 两个定价事件），再筛泰语。T035 是先从母语表收泰语设备再查行为。方向反了，后面还对这份大结果做了多次 join。
5. 昨晚推上去的 `AGENTS.md` 这次用上了（母语表、P018 归 userid、P037 不靠设备表）。对不上不是又走了 `real_geo`。那几条规则约束不了「两个渠道能不能共用一个使用分母」。
