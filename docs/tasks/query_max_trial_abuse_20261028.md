## 需求

「我们的 max 有很多试用，帮忙看下有没有薅羊毛的人。」

## 口径确认（P013 / P018-D / P032）

| 项 | 口径 |
|----|------|
| Max 限定 | `LOWER(membership)='max'`（订阅类型 max_monthly / max_yearly 等） |
| 试用（P013） | `finished` 且 `COALESCE(amountpaid,0)=0` 且非兑换码（`ordertype<>'code'` 且 snap 不含 `onetime*`） |
| 付费（P013） | `finished` 且（`amountpaid>0` 或兑换码） |
| 转化主体 | 订单侧只有 `userid`；按 userid 去重（P018-D：有账号归 userid） |
| 薅羊毛定义 | 同一 userid 产生 **≥2 笔 Max 试用单**；进一步分 **突发(burst, ≤1天)** vs 长期间隔(>30天) |
| 纯羊毛 | 突发重复试用 且 全站（任意 membership）从未付费/兑换码 |

## 结论与证据（P043）

- **确实有薅羊毛，但规模小且特征高度集中**：不是大面积真人滥用，而是一小撮「连续账号 + 秒级重复 Max 试用」的脚本/批量行为。
- 证据：突发组 118 人（占 Max 试用用户 0.38%），且 2026-06 出现 6398452→6399344 等连续 userid、每账号 2 次试用间隔仅秒级、ordertype 一致——这与真人单账号偶尔重试用的形态完全不同。
- **猜测（已标注依据与缺口）**：上述形态最可能是自动化脚本/批量注册在刷免费 Max 试用（每个 3 天试用 ×2–5 次 = 白嫖 6–15 天 Max）。但本仓只有订单副本，**未触达注册来源、设备指纹、支付/风控后台**，无法 100% 确认是外部黑产还是内部测试 harness；若要定性，需业务侧核对注册渠道与设备。
- **不要混淆**：Max 试用单（6.0 万）远超付费（1.3 万）主要是「试用→不付费」的转化问题，属正常漏斗损耗，不应都算薅羊毛；真正的滥用是上面的「重复/突发」子集。

## 补充：卡为中心「一张卡开多号各试一次」检测（2026-10-29）

用户纠正：上面 §2–§5 的「账号≥2 次试用」口径会**漏掉**真正要抓的模式——
黑产**不断开新账号、每个新号绑同一张卡再各试一次**（每号只试 1 次）。信号在**卡**上，不在账号上。
正确做法：在**全部试用**里按 `card_fingerprint` 聚合，找挂在很多不同 customer 上的卡。

- **卡数据不在 Databend**：Stripe `payment_methods.card_fingerprint` 只在 Stripe 侧，需用 **Stripe Sigma** 查（Sigma 方言，类 PostgreSQL）。
- **桥**：`imt_subscriptiongoodsorder.subscriptionid`（Stripe `sub_xxx`）→ Sigma `subscriptions.id → customer`；无需 `stripe_users`（1.3 万行分析子集、无 userid）。
- **Sigma 主查询（Query A）**：`subscriptions.trial_end IS NOT NULL` 圈全部试用 → 按 `card_fingerprint` 聚合，`COUNT(DISTINCT customer)>1` 即一张卡挂多号。`trial_end` 是 Stripe 原生「有过试用」信号，**不区分 Max/其他 tier**，命中簇需复核是否多为 Max。
