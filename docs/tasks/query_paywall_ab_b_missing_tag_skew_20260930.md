## 结论（直接回答）

### 1) A 偏多是真的，而且是分配算法问题（不是抽样巧合）

插件：

```52:64:F:/extension/utils/fake_user.ts
export async function getABTag() {
  ...
  const charCode = fakeUserId.charCodeAt(0);
  const num = charCode % AB_TAB_COUNT; // 10
  userTag = String.fromCharCode(num + "a".charCodeAt(0));
```

`fakeUserId` 大量是 SHA 十六进制（首字符只在 `0-9a-f`）。`charCode % 10` **不是均匀 a–j**。  
纯 hex 理论份额约 **A 37.5% / B 18.75% / C 18.75% / D 12.5%**（不是 30/30/20/20）。

实测（剔老号，两周几乎一样）：

| 组 | 理论 3:3:2:2 | 09/14 实测 | 09/21 实测 |
|----|-------------|------------|------------|
| A | 30% | **31.8%** | **32.1%** |
| B | 30% | **24.3%** | **24.5%** |
| C | 20% | 20.7% | 20.5% |
| D | 20% | **23.2%** | **22.9%** |

→ **B 永久少约 5.5pp 流量**；A 略多。两周份额几乎不变，**解释不了「B 本周突然少 20 单」**，但会让 B 周付费分子更小、**A vs B 的周排名更易翻**。

### 2) B 少约 18 单：拆开后不是「B 墙坏了」

09/14→09/21，B 7d 付费 **59→41（Δ−18）**（asof 拉到 09-30）。

| 拆维 | 主贡献 |
|------|--------|
| 版本 | **1.33.1：55→30（−25）**；其中量缩约 −14、费率降约 −11；1.33.3 新进 **+9**；净 −18 |
| 桌面 | 53→37（−16） |
| **同组标签 d/e/f** | **d −9，e +5，f −14** |

关键点：`d/e/f` **配置完全相同**（都是 B 臂），却一周一升两降，净少 18。  
能说明「少 20 单」主要是 **同质处理臂内的计数起伏 + 1.33.1 量/价结构**，**不是 B 付费墙配置周变更**。

注册子集：付费全在已挂 userid；注册用户付费率 0.82%→0.70%，注册人数 7198→5845——与总量缩窄同向，无单独「注册漏斗坏掉」证据。

### 3) 为什么 A 配置没变，相对结果却像「大幅波动」

机制链（不是「世界随机所以别问」）：

1. **9/7 降级后** A 注册墙优势被砍掉 → A 与 B 的付费差被压到 ≈0（T018/T047）。  
2. **周 7d 付费只有约 40–60 单/组**；再叠加 **B 分母被哈希少分 ~1/6**，B 的周分子更脆。  
3. 在「真差异≈0」时，每周「谁高」由上述小分子起伏决定 → **看起来像 A 墙在大幅波动，其实是对比组排名在抖**。A 自己绝对付费人数三周锁在 ~62（T049），并不是 A 墙转化自身大起大落。  
4. 若不修分配、仍按自然周读胜负，**AB 周表会长期不稳定**——这是实验设计/读数粒度问题，不是「放弃 AB」，而是：**当前周粒度 + 有偏分流 + 降级后效应≈0，检不出稳定差**。

### 4) 和「A 人数多」的关系

A 偏多 → A 的费率应更稳；**波动的是 A−B 排名**。根子是 **B 偏少 + 真差异被降级削平 + 周分子太小**，不是 A 人多导致 A 更抖。

## 建议（若要让 AB 结果可用）

1. **改 `getABTag`**：对 `fakeUserId` 做均匀哈希（整串 hash % 10），不要 `charCodeAt(0) % 10`。  
2. **读数**：降级后不要用单周 7d 排名拍板；用多周累计或预先算好的 MDE（当前约 50 单/周远不够分 0.02pp 级差）。  
3. **质控**：同臂内 d/e/f（及 a/b/c）周付费应同向；若像本周 f↓ e↑，先当臂内噪声，勿解读成策略差。
