## 关键结论

1. **非盗用/脚本重发，是合法但极耗 token 的电子书翻译**。10 月 4,547 条请求 input 中位数=均值=5,617、p99=5,822、max=5,951（几乎零方差）→ 固定分段；模型为 Qwen3.5-plus / Qwen3.8-flash（DashScope）+ GLM-4.7（OpenRouter）。各月 `(businessid,actionid)` 唯一性=1.0，无同请求重发。
2. **异常点在计费机制**：年付 Pro（2026-06-16 起，365 天有效）AI 额度为 **20M/月硬上限**（7–11 月计数器每月恰为 20,000,000）。用户此前可能不知该上限。
3. **流量包基本抽干**：2026-06-16 另购 10M 流量包（类型名写 500w，订单快照 OpenAITokenQuota=10,000,000），累计已用 9,995,491（**剩 4,509，≈99.95%**）。
4. **消耗节奏**：5–9 月月均 ~20M（贴上限）；10 月骤增至 26.0M（20M Pro+6.0M 包）；11 月前 7 天已 22.0M（20M Pro+2.0M 包，首周即撞破上限）。
5. **排名（全窗 5–11 月）**：169.3M token，排名 **#80 / 985,025** 活跃用户（头部 ~0.01%）。
6. **时间戳口径（P043，已更正）**：初版误判"token_used_aw 按对账日批量写入、逐日不可信"——**已作废**。数据 owner 确认该表按天同步、时间戳为正常事件时间，逐日/逐小时视图有效；个别账号事件落在少数"批次日"是真实用量落点，非时间戳损坏。
7. **行为日志待查**：3 台设备（Firefox/Win、Chrome/Win×2，均 CN）在消耗巨大的 10–11 月几乎只有 `official_page_view` 等浏览事件，**无 `translate_page` 翻译事件**；与账单海量消耗对不上。疑为电子书阅读器走独立路径/日志缺失——非盗用证据，但需前端确认日志归属。

## T104 v4 终案（2026-11-10，**已验收**）

用户最终确认根因：**该用户自行把一整个术语库（glossary / term base）塞进了每次翻译请求的 input**。因此：

1. **11-07 那 ~31K/请求的 input 是真实的**（每句实际文本才几百 token，被术语库垫成 31K），**不是账单 bug**。output 正常（~151，与实测 167 吻合）。
2. **701 请求 = 22.05M 是真实消耗**；20M Pro 上限**确被撞破**、10M 流量包**确被真实抽干**（累计 9,995,491，剩 4,509）。
3. **收回上一轮"inputusage 被账单膨胀 ~80 倍 = 计费 bug"的临时假设**（2026-11-09 晚）：当时用用户"无术语库"的对照组测试（整书 43 万、单句 387 prompt）当成真实用量，但 11-07 实际用量**带术语库**。v3 交付物的账单数字本身准确，无需改数、无需重出。
4. **行为日志缺口仍独立待前端确认**：3 设备 10–11 月 `user_behaviour` 全无 `translate_page` 事件（与账单海量消耗对不上），与术语库根因无关，是另一直角埋点问题。
5. **产品启示（非 bug，但值得优化）**：术语库每请求全量重发，致 token 消耗被放大 ~80 倍。理想做法是用缓存或把术语库放服务端/按需引用，避免用户为一致性自塞大 input。
